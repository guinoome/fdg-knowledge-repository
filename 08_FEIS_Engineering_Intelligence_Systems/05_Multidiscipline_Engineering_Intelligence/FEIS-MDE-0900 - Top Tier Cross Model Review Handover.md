**Status:** Active Future Review Handover  
**Purpose:** Guide future high-capability OpenAI and Claude Code agents in reviewing and expanding FEIS Architectural, Civil, MEPF and Auxiliary capability using verified common practice without duplicating architecture.  
**Owner / Final Authority:** Francis  
**Effective:** 2026-10-05

## Important Model-Neutral Rule

Names such as **OpenAI Astra**, **Claude Code**, **Opus**, **Fable**, **Mythos**, or future successors are execution/reviewer slots, not canonical architectural dependencies.

If any named model label changes, is unavailable, or is superseded, use the strongest available model for the assigned review role while preserving this handover.

## Mission

Review and progressively mature FEIS multidiscipline engineering knowledge covering:

- Architectural / Fit-Out / Finishes
- Civil
- Mechanical
- Electrical
- Plumbing / Sanitary
- Fire Protection
- Auxiliary / ELV
- cross-discipline coordination

Focus on real engineering/construction common practice, evidence, workflows, acceptance controls and role-specific Workbenches.

Do not create a new application simply because a profession exists.

## Mandatory First Action — Repository Audit

Before creating or changing knowledge:

1. search the full repository for the proposed capability
2. identify authoritative existing documents
3. classify the proposed change as:
   - reuse
   - extend
   - merge
   - controlled successor
   - challenge
   - new
4. identify affected Wikilinks
5. identify neighboring collaborator-owned work
6. do not rewrite another work package without authority

## Review Lanes

For major discipline reviews, use independent review lanes when practical.

### Lane A — Architecture / System Reviewer

Recommended high-capability reasoning model, e.g. OpenAI Astra or successor.

Focus:

- boundary correctness
- duplication
- shared-vs-discipline placement
- object model
- workflow architecture
- provider independence
- scalability
- acceptance tests

### Lane B — Discipline Engineering Reviewer

Recommended top-tier engineering reasoning agent, e.g. Claude Code Opus/Fable/Mythos class or successor, using the strongest available model.

Focus:

- real professional workflow
- discipline terminology
- missing engineering steps
- calculation requirements
- inspection/testing
- constructability
- common failure modes
- turnover requirements

### Lane C — Evidence / Standards Reviewer

Focus:

- source quality
- current standards
- code/regulatory separation
- manufacturer vs code vs common-practice distinctions
- clause/revision traceability
- unsupported assertions

### Lane D — Adversarial Reviewer

Focus:

- challenge assumptions
- find unsafe automation
- identify ambiguous authority
- expose missing evidence
- identify edge cases
- test cross-discipline conflicts

### Lane E — Implementation Reviewer

Focus:

- schema feasibility
- offline/local-first implications
- synchronization
- UI/workbench composition
- tests
- migration
- interoperability with Project Operations / FPJIS / FWAIS / CORE

One agent may perform more than one lane if resources are limited, but the review outputs must remain logically distinct.

## Independent-First Review Protocol

For consequential architecture:

1. reviewers inspect the canonical source independently
2. each produces findings without seeing the other reviewer's final conclusion where practical
3. findings are compared
4. agreements are consolidated
5. disagreements become a conflict/debate record
6. evidence is gathered
7. Francis/Nex governance resolves architecture changes

Avoid false consensus created by one model merely rewriting another model's answer.

## Evidence Priority

Prefer, in order appropriate to the question:

1. laws / regulations / official authorities
2. official codes and standards
3. authoritative professional bodies
4. manufacturer technical documentation for product-specific facts
5. contractual/project documents
6. recognized engineering manuals/guides
7. established industry common practice
8. secondary training material
9. informal community evidence

Common practice must not be promoted to mandatory code unless supported.

## Review Output Contract

Every review must produce:

### A. Scope

What discipline/system/workflow was reviewed.

### B. Existing Canonical Knowledge

What already exists and should be preserved.

### C. Verified New Knowledge

What evidence supports the addition.

### D. Common-Practice Findings

Useful recurring practice that is not necessarily mandatory.

### E. Standards / Regulatory Findings

Requirements with authoritative source.

### F. Assumptions / Unknowns

What remains uncertain.

### G. Gaps

Missing capability.

### H. Duplication Risks

Where new material would recreate an existing capability.

### I. Proposed Repository Change

Exact files to create/update.

### J. Wikilink Plan

Parent, related, dependency and successor links.

### K. Acceptance Tests

How the new knowledge or implementation will be validated.

### L. Conflicts

Any reviewer disagreement or cross-system boundary issue.

## Common-Practice Review Questions

Ask:

- What do experienced practitioners repeatedly do?
- What information do they capture?
- Which decisions recur?
- Which errors recur?
- Which checks occur before work starts?
- Which records prove the work?
- Which approvals are required?
- Which interfaces most often fail?
- What should survive personnel turnover?
- What can be standardized?
- What must remain project-specific?
- What can be deterministic?
- What requires professional judgment?

## Mandatory No-Rewrite Rule

A reviewer may identify defects in another collaborator's work but must not silently rewrite it.

Use:

- finding
- evidence
- proposed patch
- successor artifact
- issue
- debate record

until authorization is clear.

## Provider / Tool Neutrality

Do not hard-code architecture around:

- Claude
- OpenAI
- Gemini
- a specific IDE
- one MCP
- one vector database
- one cloud platform
- one CAD/BIM vendor

Store capability definitions in FDG-controlled knowledge and schemas.

## High-Risk Engineering Rule

A model may assist with:

- extraction
- comparison
- summarization
- drafting
- workflow guidance
- anomaly detection
- evidence assembly

It must not independently certify:

- structural safety
- electrical protection
- fire/life-safety compliance
- regulated design compliance
- final engineering acceptance
- contractual entitlement
- billing approval

without the governing professional/organizational authority and validated methods.

## Review Cadence

Recommended future pattern:

- review a discipline when a new project/use case exposes a meaningful gap
- run a broader discipline review before commercial packaging
- re-review when major standards/regulations change
- re-review after significant operational lessons
- avoid arbitrary rewrite cycles that create churn without new evidence

## Final Deliverable

A successful review leaves the repository more useful to the next qualified engineer or agent without making it more duplicated, more provider-dependent, or less traceable.
