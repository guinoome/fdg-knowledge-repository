## Quality objective

“Astra-level Markdown” means rigorous, explicit architecture and implementation instructions that reduce rediscovery and ambiguity. It describes artifact quality, not a requirement to use Astra. Apply it across older, lower-cost, local and future agents. Identical model intelligence or results cannot be guaranteed; acceptance evidence establishes bounded implementation quality.

Before coding, create or update a task-specific Markdown package in GitHub. Reuse approved packages when their scope, contracts, source versions and validation remain applicable; write a delta for material changes.

## Required concreteness

Retain every A–Q section and the context capsule. Complete task-specific:
- repository checkpoint, source read order, applicable readiness and existing authorization;
- evidence-to-reference-to-requirement-to-blueprint mapping;
- existing capability reuse and selected architecture with reasoned alternatives;
- exact file/component change map and ownership boundaries;
- schemas, types, units, formulas, rounding, state transitions and invariants;
- API/event interfaces, errors, retries, idempotency and permissions where applicable;
- local-first storage, offline behavior, sync/conflict handling and provider adapters;
- screen/workflow states and user acceptance behavior where applicable;
- ordered build steps with action, path/symbol, dependency, expected result and verification;
- task-specific fixtures, inputs, expected outputs and tolerances;
- meaningful verification commands grounded in the actual repository, not invented commands;
- recovery, completion evidence and escalation triggers.

Use N/A with a reason where appropriate. No blocking placeholder may remain in an executable package. A concise bounded fix may reuse contracts by reference rather than duplicate a large blueprint.

Unvalidated external claims cannot silently become engineering acceptance rules.

## Golden Path step form

| Step | Dependency | Exact action / file / symbol | Expected behavior | Check / expected output | Failure / escalation |
|---|---|---|---|---|---|

Specify formulas or pseudocode when logic would otherwise be ambiguous. Explain decisions once in the full package and point to them from the capsule.

## Ready-to-code check

The receiving builder verifies sources, version deltas, contracts, file boundaries, required inputs and acceptance criteria. Applicable work-package readiness reaches 100%, no hard blocker remains, and existing build authorization covers the work. Reference research and this contract do not grant build or deployment authorization.

If architectural ambiguity remains, report the precise gap and continue independent authorized work where possible. Do not compensate by guessing.

## Finished session

Choose a bounded vertical slice that produces an accepted usable outcome. Return implemented requirements, checks passed/failed/not run, evidence paths, changed files, actual commit, remaining limitations, status/manifest updates and next work package. End CLOSED or BLOCKED WITH EVIDENCE. Never inflate completion from a written plan.

## Learning and efficiency

Record clarification count, rework, acceptance success, elapsed effort and cost where measurable. Reuse unchanged evidence by source/version and scope; recheck changed dependencies, expired evidence and invalidated assumptions. Agent identity alone is not proof that knowledge remains current.

Keep durable architecture in the full package, small actionable context in the capsule, and task results in the repository. Evaluate quality by reproducibility and passing acceptance criteria, not Markdown length or model prestige.
