## Source-of-Truth Rules

- **FDG Ecosystem — Center** governs repository-level navigation and the cross-system mother map.
- **Nex Core** governs engineering and organizational operating standards.
- Each intelligence system's **Master Index / Home** governs that system's internal structure.
- Individual governed documents contain the substantive standard, decision, evidence, or domain intelligence.
- **Projects** execute work; they do not automatically redefine canonical architecture.
- New findings become organizational knowledge only through the appropriate review, validation, linking, and promotion path.

Do not create duplicate authoritative documents just to make navigation easier. Link to the canonical source.

## Governance Principles

1. **Review before redesign.** Never redesign an approved system from memory.
2. **Extend; do not silently overwrite.** Preserve approved baselines and superseded history for traceability.
3. **Evidence over confidence.** Separate verified fact, assumption, inference, proposal, and unresolved question.
4. **One authority per concept.** Avoid competing standards, duplicate master indexes, and conflicting architecture descriptions.
5. **Knowledge must compound.** Project experience should become reusable organizational capability rather than remain trapped in one conversation, tool, or collaborator.
6. **Organizational capability outranks tool optimization.** Models, agents, applications, and platforms are replaceable resources; FDG knowledge and governance must remain portable.

## Collaboration and Agent Operating Rule

Any collaborator, model, coding agent, research agent, or future automation working with this repository should begin by reading the current governed context before proposing changes.

Minimum navigation sequence:

```text
README
→ FDG Ecosystem — Center
→ Nex Core / relevant governance standard
→ relevant system Master Index
→ relevant project and evidence
→ proposed work package
```

A collaborator must not assume that a file is authoritative from its filename alone. Check its status, backlinks, governing index, related decisions, and superseding records.

Before a long-running collaborator session ends or approaches service limits, it should leave a concise handover containing the objective, evidence reviewed, decisions made, files changed, tests performed, unresolved issues, risks, and next executable action.

## Engineering Output Standard

Every document should reduce ambiguity rather than increase word count.

Prefer:

- explicit objective and scope;
- evidence and source traceability;
- concrete engineering decisions;
- constraints and interfaces;
- measurable acceptance criteria;
- assumptions and unresolved questions;
- implementation guidance that another qualified person or agent can execute.

Avoid generic filler, repeated statements, unsupported claims, unnecessary sections, and architecture added outside the assigned work package. If removing a paragraph does not reduce implementation or organizational understanding, remove it.

## Projects vs. Knowledge

A project is a temporary execution structure. The repository is the long-lived organizational memory.

```text
Observation / Project Evidence
          ↓
Analysis and Decision
          ↓
Validated Lesson / Standard / Pattern
          ↓
Governed FDG Knowledge
          ↓
Reusable Capability in Future Projects
```

This separation allows FDG to improve across projects without allowing one implementation, collaborator, or technology stack to become the architecture of the entire ecosystem.

## Local and GitHub Synchronization

The root `README.md` in the local FDG Knowledge Repository and the root `README.md` in this GitHub repository represent the **same document**. They must not evolve as separate narratives.

When synchronized, both copies should contain the same repository-wide description and navigation model. Git history provides version traceability; the local knowledge repository remains the working knowledge environment.

Before changing architecture, pull/review the latest governed state. Before publishing changes, verify links, document status, conflicts, and repository integrity.
