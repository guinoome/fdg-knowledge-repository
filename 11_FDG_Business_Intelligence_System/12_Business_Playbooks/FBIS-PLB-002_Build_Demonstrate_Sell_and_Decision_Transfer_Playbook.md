## 0. Policy: four forms of proof, not “app built = product sold”

```text
FDG knowledge and demonstrated expertise
  → one actual buyer pain (commercial hypothesis)
  → one bounded scope and independently reviewable outcome
  → demand proof (real conversations, order, verified paid pilot)
  → delivered result, professional acceptance and measured unit economics
  → repeatable procedure + transferable operator/decision boundaries
  → targeted automation in an authorized local work package
  → software/recurring subscription only if evidence justifies it
```

**Do not mistake:** prototype for deliverable; expressed interest for sale; proposal for paid order; payment for accepted delivery; accepted first order for subscription renewal; delegated execution for delegated authority; knowledge completeness for operational maturity; internal productivity for a customer market.

This playbook does not supersede [[11_FDG_Business_Intelligence_System/11_Business_Frameworks/FBIS-BP-003_FDG_First_Payout_Commercial_Validation_Portfolio|FBIS-BP-003]] prices/priorities, [[11_FDG_Business_Intelligence_System/11_Business_Frameworks/FBIS-BP-004_FDG_Outcome_to_Learning_Business_Operating_Loop|FBIS-BP-004]], [[14_FDG_Service_Intelligence_System/04_Service_Packaging/FSvIS-PKG-0001 - Service Packaging Standard|FSvIS packaging]], [[20_FPJIS_FDG_Project_Intelligence_System/33_First_Payout_Commercial_Validation_Blueprints/19_Pilot_001_Maintenance_Reporting_Commercial_Execution_Charter|Pilot 001]], [[06_Organizational_Architecture/DELEGATION_STANDARD|delegation]], or [[20_FPJIS_FDG_Project_Intelligence_System/33_First_Payout_Commercial_Validation_Blueprints/08_Local_Validation_Release_and_Deployment_Gates|local release gates]].

## 1. Pick one marketable capability already owned by FDG

The founder's strongest hypothesized *paid capability* is not generic vibe coding: it is **engineering-grounded operational evidence → management decision-ready outputs**, using existing FEIS, FBPOIS, service, project and knowledge standards.

A marketable capability record has:
- `capability_id` and existing canonical origin, competence and lawful scope;
- `buyer_role`, `payer_role`, `pain_trigger`, `current_workaround`, `measurable_loss_or_unknown`;
- `deliverable`, `needed_customer_inputs`, `professional_review`, `limits/exclusions`;
- `evidence_source`, `example_fixture`, `actual_client_acceptance`, `repeat_frequency`;
- `commercial_offer_id`, `price_rule_ref`, `trial_delivery_cost`, `support_burden`;
- `working_operator_role`, `reviewer_role`, `approval_scope`, `handover_ready`.

Do **not** open a parallel “Founder Skills Database.” Add references to existing FBIS opportunity + FSvIS offer + FPJIS work package records. High-income skill selection is a *market-outcome test*, not a call to learn more coding before first outreach.

## 3. Current commercial path — make the first customer before the next platform

**Use existing 30-day targets:** 20 qualified prospects, 5 meaningful buyer conversations, 2 formal offers and 1 independently verified paid pilot. These are targets, **not actual results** or an automatic success criterion; prospective per-offer threshold changes require documented approval.

1. **Discover buyer:** qualified decision-maker, actual recent event, manual workaround, current contract/tool cost, need, cadence, data availability, ability to pay.
2. **Demonstrate outcome:** one truthful sample, what client must supply, outputs and limits. No invented facility readings/photos/compliance conclusions. Demonstrate the *result*, not the AI or code.
3. **Package offer:** FSvIS-defined deliverables, assumptions, omissions, reviewer, revision cap, acceptance criteria, realistic completion basis, versioned FBIS experimental price and approved payment path.
4. **Ask for real decision:** documented interest → qualified opportunity → issued offer → client order → **independently verified actual collection** as separate states. No unsanctioned outreach or collections.
5. **Deliver manually where feasible:** use existing P001-R01..R10 private operational records, engineering input coverage, technical signoff and client acceptance.
6. **Measure:** cash receipts net of transaction fees, actual founder + reviewer hours, direct cost, unsupported data/claims, revision/support time, client outcome, renewal signal and acquisition friction.
7. **Learn:** if willing payer but delivery too costly, fix the process/price; if buyer unwilling, inspect segment/problem/offer rather than automatically code; if repeated buyer outcome and stable workflow, design **one** separately authorized narrow product/automation patch.

### Example one-sentence paid promise (DRAFT, needs service scope and buyer verification)

“For a facility engineering team struggling with fragmented monthly maintenance records, FDG prepares one engineering-reviewed monthly evidence and action report from the records you provide, identifying documented gaps and outstanding actions under an agreed scope and price.”

Do not claim an inspection happened, eliminate missing input warnings, or market unverified percentage/time savings.

## 4. Founder Time-Back / Delegation Pilot

The source suggests **Audit → Transfer → Fill**. Implement as an observable work-package experiment, not a blanket instruction to delegate all administration to a chatbot.

### Audit — measure work before automation

Private ledger fields:
```yaml

founder_minutes: null
qualified_review_minutes: null
error_and_rework_minutes: null

```
Good initial candidates **after actual work is observed**: preparing a *draft* customer reply, sorting evidence and follow-up tasks, formatting one approved monthly report, generating draft quotation inputs, detecting missing PM checklist fields. Not automatically eligible: professional engineering acceptance, certifying compliance, final payment/refund, procurement approval or unsupervised client communication.

### Transfer — freeze a bounded operator pack before delegating

Each transfer must contain:
- `work_package_id`, original demonstration with **consent and safe data**, written steps, input/output contracts, approved examples;
- distinct `operator`, `accountable_owner`, `technical_reviewer`, `decision_rights`, `forbidden_actions`;
- permitted source data, classification, source-level and document-level access policy, retention/deletion and audit log;
- exception and escalation cases, rollback/fallback, acceptance tests on normal/boundary/adversarial fixtures;
- handover artifact with no hidden dependency on the founder's chat history or a named model/vendor;
- measured trial result. **A recorded screen/video is input to drafting, not an approved automation or delegated authority.**

Net founder time recovered should be calculated transparently:
```text
Net Founder Minutes Recovered
 = Old Founder Minutes
 - New Founder Execution Minutes
 - New Founder Review / Corrections / Interruptions Minutes
```
Report additional human review, transferred staff labor, API/tool costs, errors and customer quality *separately*. A negative result is a stop/improve signal; no imaginary 20-hour/week claim.

### Fill — reinvest capacity in high-value roles

Candidate replacement blocks: real customer discovery, solution review, engineering calculations and competent technical judgment, commercial proposal quality, distribution, relationship management, capability documentation and staff training. **Do not refill regained capacity with unvalidated speculative apps**.

## 5. Decision-Transfer and FDG Organizational Memory

A “second brain” already exists conceptually as approved knowledge repository + [[10_FDG_CORE_Intelligence/FDG-CORE-STD-007_MEMORY_AND_CONTEXT_ENGINE_STANDARD|Memory & Context Engine]] + project context. No separate Apex/other provider platform is required.

Capture *reusable decision contracts*, not indiscriminate meeting transcripts:
```yaml
decision_case_id: ""
scope_and_applicability: ""
relevant_governing_standard_refs: []
context_and_input_evidence_refs: []
allowed_role_and_authority: ""
decision_options: []
thresholds_and_why: ""
escalate_if: []
prohibited_outcomes: []
accepted_output_examples: []
technical_or_commercial_reviewer: ""
date_and_version: ""
security_access_class: ""
next_review: ""
```

Example for maintenance reporting: an operator can classify the status of **evidence received**, flag a missing pump test log and draft a gap request. The operator **cannot** certify that the test passed or claim PM completion when supporting evidence is absent; that requires defined competent review/authority. This transfers repeatable decisions without transferring unsafe judgment.

**Privacy stop:** Do not upload raw HR, salary, contracts, personal conversations, customer financials, identifiable cases or facility-sensitive data into the public repository. Meeting/screen/audio capture requires legitimate authority and notice/consent where applicable. Retrieval permissions must be enforced *before* model context assembly; sanitizing outputs by prompt alone is insufficient. Require wrong-role/wrong-client/revoked-access negative tests.

**Founder dependency resilience test:** Ask a separately authorized competent operator to deliver the same bounded task from the approved package with the founder unavailable. Measure unanswered queries, escalations, errors and acceptance; fail if success depends on unrecoverable chat messages or private undocumented founder knowledge.

## 6. FDG 90-Day “build small → sell → transfer” experiment (planned, not scheduled or launched)

| Period | Primary deliverable | Proof to retain | Fail/redirect condition |
| --- | --- | --- | --- |
| Days 1–30 | One commercially approved narrow service offer, five target interviews within the existing 20/5/2/1 funnel and an honest pilot proposal; first verified paid pilot only if achieved | Demand record, consented interview summary, frozen offer, payment evidence when real | No grounded pain or buyer: revise/stop; do not build a new app merely to demonstrate activity |
| Days 31–60 | One complete engineering-reviewed service delivery **if** a buyer engaged; first operator SOP and accepted example | Input/source register, reviewer, client acceptance, actual effort/cost, first missing-data/exception list | Incomplete evidence, safety/competency gap or poor unit economics: pause/reprice/rescope |
| Days 61–90 | One bounded independently reviewed delegation/time-back trial or local-only prototype for a repeated verified bottleneck | Work-package authority, test/rollback, new founder minutes, errors, transferred staff cost, repeat buyer evidence | If demand unproven, keep manual research; if automation accuracy/security weak, do not deploy |

The 90-day period is a **suggested learning horizon**, not permission to bypass the current Pilot 001 or preapproved engineering safety gates. No weekly cadence, emails or buyers are automatically created.

## 7. Optional internal engineering improvement sprint / micro-hackathon

Use the transcript's 2–3-person real-problem prototype exercise **only after** a safe task is chosen. Require:
- Business/workflow owner states a real repeated problem and baseline.
- Separate qualified reviewer confirms acceptance, security, data minimization and competence.
- Team time-boxes work to a small **finished** workflow and uses sanitized fixtures.
- Demo must be interactive and show input → output → error/exception → review → rollback; static animation alone is insufficient.
- Independent FPJIS validation and release gates still apply. No self-approved production integration.
- Promote one proven reusable procedure/contract to knowledge with owner and provenance; reject tools with no practical savings or unacceptable maintenance cost.

**Metrics:** accepted task completion; quality/rework; true net time recovered; operator transferability; owner/reviewer effort; ongoing maintenance cost; coverage; permission denial negative tests. **Not metrics:** number of vibe-coded apps, screenshots, total code generated or claimed “10x”.

### Work-package acceptance gates
- **BSS-AC-01:** Source skill and buyer/problem evidence are differentiated; no claims based on unverified testimonial.
- **BSS-AC-02:** One offer reuses existing FBIS, FSvIS and FPJIS identities; no new parallel customer registry/CRM.
- **BSS-AC-03:** Sales evidence correctly separates prospects, committed orders, independently verified payments, delivered and accepted results, actual renewals.
- **BSS-AC-04:** Human engineering and release authority and data restrictions remain effective through the entire loop.
- **BSS-AC-05:** Actual founder/reviewer/employee effort, cost, rework and risks are measured before claiming “buyback”.
- **BSS-AC-06:** Transferred work can be completed by another authorized operator with tested good/bad/exception cases; source access enforced before retrieval.
- **BSS-AC-07:** Vendor replacement or expired subscription does not erase canonical SOP, decision, evidentiary history or work-package artifact.
- **BSS-AC-08:** New software, agents, bulk client messaging, payment collection and remote deployment cannot be inferred from this document.
- **BSS-AC-09:** FAIS independent audit can reconstruct selected price, source-backed technical output and commercial decision.
- **BSS-AC-10:** Negative demand and failed transfer experiments are preserved as valuable learning without inventing a success claim.
