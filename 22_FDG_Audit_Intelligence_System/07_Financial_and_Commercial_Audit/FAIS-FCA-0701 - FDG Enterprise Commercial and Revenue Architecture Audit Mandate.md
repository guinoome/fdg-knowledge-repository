## 5. Evidence Classification

Every material statement in the audit working papers and final report must be labeled as one of the following:

| Classification | Meaning | Required handling |
|---|---|---|
| **Verified Fact** | Directly supported by authoritative evidence appropriate to the claim | Cite the exact source and relevant section, page, record, or line where practical; a draft/candidate file can verify that a statement exists, but not that the statement is true in law or operations |
| **Working Hypothesis** | Plausible model or interpretation requiring validation | State what evidence would confirm or reject it |
| **Decision** | Explicitly approved choice by the authorized decision-maker | Record decision owner, date, scope, and affected records |
| **Unresolved Question** | Material uncertainty that cannot yet be answered | Assign evidence needed, responsible party, and closure condition |
| **Audit Requirement** | Mandatory procedure or evidence gate imposed by this mandate | Track completion and exceptions |
| **Recommendation** | Evidence-based proposed action that is not yet approved | Classify as KEEP / LINK / MERGE / MODIFY / CREATE / DEPRECATE |

Do not silently convert conversation statements, filenames, draft documents, imported research, plans, or candidate architectures into verified facts.

Use two independent evidence fields where relevant: **artifact existence/status** and **substantive truth/applicability**. For example, a proposed FBIS file may verify a candidate model exists while leaving the model's real-world validity unresolved.

The classifications above describe the status of a statement. KEEP / LINK / MERGE / MODIFY / CREATE / DEPRECATE describes a proposed action. A statement may therefore be a Verified Fact supporting a MODIFY recommendation without conflating the two classifications.

For this audit, a matter is **material** if it could change entity identity, legal authority, registration, tax or accounting treatment, ownership, IP rights, professional responsibility/liability, customer money or data, security/privacy obligations, the selected recommendation class, or the decision to proceed commercially. A **high-impact unresolved matter** is a material matter that could make an offering unauthorized, noncompliant, misleading, financially misstated, professionally unsafe, or difficult to reverse.

## 9. Mandatory Audit Sequence

Execute the following sequence without skipping or reordering the creation gate:

> **Discover → Map → Detect overlap/gaps → Reuse existing ownership → Design integration → Only then create missing architecture**

Iteration among Discover, Map, and Detect overlap/gaps is permitted and expected. The non-negotiable control is that Reuse existing ownership and Design integration must be exhausted before any CREATE recommendation.

### Phase 1 — Discover

1. Read repository governance and entrypoints before domain files.
2. Record the current Git branch and status; treat all pre-existing uncommitted work as protected input unless separately authorized.
3. Inventory relevant authoritative, approved, draft, candidate, archived, imported, and operational records.
4. Search exact terms and conceptual synonyms; do not rely only on expected filenames.
5. Identify real-world evidence that is missing from the repository and must be requested or professionally verified.
6. Capture the audit timestamp, current commit, status inventory, and SHA-256 hash of every cited working-tree file. For external sources, record retrieval time, issuing authority, direct URL or record identifier, and source version/date.

### Phase 2 — Map

Map every relevant responsibility to its current owner, evidence, authority level, interfaces, inputs, outputs, and downstream consumers.

At minimum map:

- ecosystem and organizational identity;
- legal entity and operating brand;
- products, services, platforms, and projects;
- registered activities and lines of business;
- contracts and commercial terms;
- invoices and tax classification;
- payment and collection;
- accounting/ERP and financial reporting boundaries;
- tax and compliance evidence;
- IP ownership and licensing;
- revenue and profit attribution;
- engineering professional responsibility and liability;
- subscription, entitlement, and usage evidence;
- future corporations and migration triggers.

### Phase 3 — Detect overlap, contradiction, and gaps

Compare claimed owners and identify duplicate ownership, incompatible terminology, broken links, stale indexes, missing evidence, unclear interfaces, responsibility gaps, and places where a dashboard or project document improperly acts as a system of record.

### Phase 4 — Reuse existing ownership

Prefer existing governed owners. Add links or clarify interfaces before proposing a new architecture component. A weak or incomplete owner is normally a MODIFY or LINK case, not automatic permission to CREATE.

### Phase 5 — Design integration

Design a responsibility and traceability model across existing systems. Preserve one primary owner per responsibility and explicit consumer/provider interfaces.

### Phase 6 — Create only if proven missing

Creation is permitted only when the evidence register shows that:

1. no existing owner has the responsibility;
2. assigning it to an existing owner would violate that owner's boundary;
3. the proposed addition has a clear owner, purpose, interfaces, lifecycle, approval path, and no duplicate authority; and
4. the Founder approves the creation recommendation.

### Phase 7 — Approval and implementation separation

The audit executor may recommend but may not self-approve. The Founder is the final internal decision owner for audit scope, repository architecture, and CREATE / MERGE / DEPRECATE actions unless a governed repository record assigns that authority elsewhere. Qualified legal, tax/accounting, privacy/security, and professional-engineering review is additionally required when applicable; Founder approval does not replace statutory or professional authority. Record each approval, condition, dissent, and unresolved exception in a decision record before implementation.

## 14. Recommendation Classification

Every recommendation must use exactly one primary class:

| Class | Use when | Minimum evidence |
|---|---|---|
| **KEEP** | Existing ownership and content are correct and sufficient | Verified owner, boundary, current status, and working links |
| **LINK** | Correct owners exist but interfaces or navigation are missing | Both endpoints, responsibility boundary, and required relationship |
| **MERGE** | Two records or structures duplicate the same responsibility | Proven overlap, authority decision, provenance and preservation plan |
| **MODIFY** | Existing owner is correct but content, boundary, terminology, or control is incomplete/inconsistent | Exact defect, impact, smallest bounded correction, validation plan |
| **CREATE** | Responsibility is genuinely unowned and cannot fit an existing boundary | Completed search, rejected alternatives, owner, interfaces, lifecycle, approval |
| **DEPRECATE** | Material is superseded, misleading, or unsafe to remain active | Successor/authority, preserved history, inbound-link plan, approval; do not delete by default |

Each recommendation must cite actual repository files and any authoritative external evidence. A recommendation without an evidence trail is incomplete. When remediation needs multiple actions, decompose it into separately approvable steps, each with one primary class—for example MODIFY an owner boundary, then LINK its consumer.
