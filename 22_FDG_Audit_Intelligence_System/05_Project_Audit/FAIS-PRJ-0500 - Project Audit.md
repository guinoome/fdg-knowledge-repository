# Project Audit

## Purpose

Audit project definition, requirements, controls, evidence, change, risk, economics, lifecycle decisions, and closeout.

## Audit Areas

Charter, scope, requirements, baseline, traceability, deliverables, definition of done, assumptions, decisions, changes, dependencies, risks, cost/schedule evidence, acceptance, handover, and postmortem.

## Interface

FPJIS may manage project intelligence; FAIS evaluates whether project controls and evidence meet approved criteria.

## Stage Assurance

Use stage or milestone gates only where defined. Do not invent project gates after the fact and claim they were mandatory.

## Control Note

This document is part of the initial FAIS baseline. It may be expanded through controlled future milestones. Recommendations do not become FDG policy until approved through the applicable governance authority.

## Functional Product Delivery Evidence — 2026-10-17

FAIS must independently distinguish approved concept, implementation source, runnable artifact, executed test results, bounded functional-user acceptance, real operational acceptance and commercial proof. It must reject unsourced claims that documentation or prototype screens equal useful functional products. Do not self-certify by rewording a checklist.

First scoped source/evidence audit: [[22_FDG_Audit_Intelligence_System/05_Project_Audit/FAIS-PRJ-0501 - Functional Product Evidence Audit 2026-10-17|2026-10-17 Functional Product Evidence Audit]]. It examines selected QTO, Construction Lifecycle, Business Platform and FBPOIS spatial files, records concrete positive code evidence alongside blocking gaps, and explicitly **does not** claim fresh runtime testing or repository-wide coverage. FAIS owns audit/findings; FPJIS owns release and project gates; domain experts own technical acceptance.

## Four-Question Independent Professional Challenge — 2026-10-19

**Founder discussion captured; proposed audit checklist within this existing FAIS baseline.** This supplements, not replaces, project controls or qualified human acceptance. Apply in **four short lines per consequential claim** (reasons, exact sources, expected/actual evidence), not a new document or ceremony:

| Challenge | Required evidence/output | Do not mistake for proof |
| --- | --- | --- |
| **What would a top professional do that was not asked?** | Record at least one material omitted risk, alternative, assumption or user-impact check, or a reason none was found after challenge. Name reviewer and disposition. | A longer feature wish list or model's confident prediction |
| **What raw material would they start from?** | Pin original client need, approved decision, baseline source code and commit, genuine operating records/instrument data, applicable engineering reference, current artifact/contract as relevant. Label source freshness and permission. | A generated recap, mock visual, remembered discussion or unverified claims |
| **Which methods and tools would they use?** | Identify an appropriate repeatable measurement, manual reference computation, automated test, code review, browser/device test, security/permission check, engineering standard or controlled user test; report tool/version, scope and what was NOT run. | Tool brand prestige or automatically generated test counts |
| **What, other than the AI, shows the result is right?** | Independent expected results; repeatable input/output; relevant physical measurements; authorized domain/engineering or client acceptance; verified payment/value where claimed. Identify who checked, when and on which release. | Self-awarded pass, agreeable agents or a pleasant demonstration |

When a material question has **no external answer**, verdict is **UNVERIFIED / NEEDS EVIDENCE**. An auditor cannot award production/client/financial readiness from documentation completeness. Ensure human authority is real, not impersonated, and never invent engineering limits. For small low-risk tasks, a four-row paragraph/table in the existing acceptance record is sufficient.
