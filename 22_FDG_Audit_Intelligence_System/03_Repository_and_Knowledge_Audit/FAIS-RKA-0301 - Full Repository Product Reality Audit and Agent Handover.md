## 3 — Full-repository coverage procedure (mandatory, repeatable)

Perform the audit on a **pinned SHA**; do not base it on moving main without a checkpoint.

**Pass A: inventory and ownership.**
1. Determine repository(s), accessible branch, HEAD commit, permissions and whether other local-only/connected repositories exist. Only claim what can actually be accessed. A GitHub mirror is not automatically equivalent to an uninspected Obsidian vault or a production deployment.
2. Enumerate every tracked path, preferably with git or paginated GitHub tree/contents traversal; code search is insufficient if not indexed. Record tree API truncation/pagination; never treat a partial result as exhaustive.
3. Classify each tracked path as governance, canonical architecture, project source, test, deploy/build, release evidence, image/binary, reference/import, obsolete/historical (preserved), generated artifact or unknown. Record path, hash, owner/system, current/historical, source authority and audit disposition.
4. Audit ALL tracked top-level areas including Nex/governance/identity/agents/knowledge architecture, FEIS, Integration, FDG CORE, FBIS and OLD archives, FSIS, FLIS/FRCIM, service, FBPOIS, FPIS, FEXIS, FWAIS, FPJIS, FMCIS, FAIS, Projects/Active and other Projects, docs, GitHub workflows, root AGENTS.md/CLAUDE.md and integration tools. Reserved/missing system numbers are not invented folders. Enumerate each nested active project and subrepo/mirror separately.
5. Maintain one coverage register with path counts and clear outcomes: **INSPECTED**, **AUTOMATICALLY CHECKED**, **DEFERRED (reason/owner)**, **INACCESSIBLE**, **NOT APPLICABLE (reason)**, **UNKNOWN**. A repository-wide audit claim requires 100% tracked-path coverage disposition, not necessarily manual reading of every PNG or generated HTML.

**Pass B: architectural truth.**
- For each system, identify single canonical authority, approved vs draft vs candidate, dependencies, duplicates, conflicting naming/schema, broken/basename-ambiguous wikilinks, missing source evidence, superseded rules and legal/engineering version/date authority.
- Do not restructure directories, overwrite peer work, delete historical decisions or rename canonical modules for tidiness. New evidence produces explicit proposed amendment/patch, decision, exact diff and backlinks.
- Compare prior user decisions to repository records and agent handovers. Use actual retrievable sources; flag missing discussion-to-repository transfer as **NOT CAPTURED / NEEDS RECONCILIATION**, do not guess. Do not ask the founder to repeat an answer already accessible in approved artifacts.

**Pass C: product/source reality.**
- Inventory each distinct actual app/product; record path/repo, branch/commit, runnable entrypoint, build command, runtime stack, data storage, offline support, tests, release method, access/roles, local-first/provider-neutral contract, deployment and known users.
- Link **need → accepted scoped requirement → architecture/design → exact source → test case → actual run/evidence → user acceptance → measured operational/commercial result**. Clearly mark absent edges.
- Verify what is REALLY WORKING from code plus actual runtime tests when tooling/environment permits; otherwise record **NOT EXECUTED** and precise repro commands. Test normal, boundary, negative, permission, persistence/restart, offline/sync, rollback/recovery and mobile when applicable. Separate synthetic vs real-world evidence.
- Distinguish **CONCEPT**, **CODE PRESENT**, **HISTORIC TEST EVIDENCE**, **FUNCTIONAL CANDIDATE**, **FUNCTIONALLY ACCEPTED**, **OPERATIONALLY VALIDATED** and **COMMERCIALLY VALIDATED**. Record the accepted *scope*, not an inflated project percentage.
- Preserve functional, already-tested offline QTO, Construction Lifecycle, solar, business and facility modules. No duplicate scaffolds. Independent real-person engineering/customer acceptance must never be impersonated by an agent.
- When permission, payment, personal/tenant data, engineering safety, and regulatory controls cannot be verified, **FAIL CLOSED** for the related action. Never run live payment, production schema migration, credential changes or deployment without specific permission.

**Pass D: gap and risk triage.**
- Each finding: ID; project/system; observed condition; exact path/line/commit; expected behavior/approved source; consequence; type (missing decision, source drift, defect, security, usability, verification, unimplemented feature, overlap); risk P0–P4; smallest solution; owner; test; required authorization; status.
- P0: credible data loss/unsafe engineering/security or unauthorized finance; P1: core user flow blocked or false production claim; P2: customer/engineering adoption blocker; P3: experience/usability or cost; P4: future/optional. No unsupported numeric readiness promotions.
- Prioritize **finished, valuable end-to-end products**, not new frameworks. Begin with runnable candidate and smallest blocker where safe. For each patch, estimate benefit, effort, risk and cross-product reuse; avoid spending implementation budget on nice-looking documentation.

## 6 — HOW the top-tier agent teaches an older model to build correctly

Think like a senior engineer giving a qualified junior a precise field work order:
1. **First explain the user outcome in one sentence:** "When the technician captures X offline and returns, Y persists and Z report is produced."
2. **Show what already works:** exact current code and "do not touch" files, plus original test case.
3. **Give deterministic numbered instructions:** edit this file → add this function → call this existing contract → run this test → expect this visible value/state. Define important decisions, input/output, formula, permission, data and errors before delegation.
4. **One task, one owner, one testable outcome:** keep tasks independent and short enough for older contexts. Provide exact file paths plus only necessary context. No expectation that the old model should understand a whole enterprise architecture.
5. **Provide runnable fixtures and exact acceptance answers:** normal + failure + boundary; for engineering use qualified-approved reference results, never invented thresholds.
6. **Require a concise return:** changed file list, test command/results, screenshot/output if needed, remaining defects, exact commit and handover.
7. **Stop condition:** If a contradiction, missing rule, unauthorized change, safety concern, inaccessible dependency or failing critical test arises, **STOP AFFECTED SCOPE — REPORT BLOCKER**. Top-tier resolves it and issues an amended card. Do not guess, silently redesign or claim completion.

**Readability requirements:** elementary plain English, one term for one concept, numbered steps and small examples; short front-page task card with optional advanced annex; no unexplained acronym soup, no vague "make it better" and no top-tier-only reasoning phrases. A model that does not support a specialized framework must still be able to follow the plain Markdown card.

**Protection:** never ask an older model to run an external network/deployment/payment command that the current environment cannot authorize; never hand it secrets or sensitive client data; no provider-lock-in. Working software takes precedence over ornamental documents.

## 7 — Stop, escalate, and closure gates

**Escalate to top-tier reviewer** when: current source contradicts approved governance; data/security/authority/design ambiguity would require invention; cross-team files overlap; an engineering acceptance rule has no approved source; tests show nonlocal regression; deployment/payment/security authority is absent; or the intended user output is not demonstrably useful.

**Stop full-audit completion claim** until:
- complete **tracked path coverage disposition** and all unaccessed scopes explicitly identified;
- system/authority graph reconciled without silent overwrites;
- every accessible actual product assigned a source-backed scope/status with X = NOT RUN for unexecuted tests;
- high-risk findings and remediation owners recorded;
- findings and recommended cards linked into existing indexes and project handovers;
- every patch actually performed has diff, test/regression/rollback evidence and owner disposition;
- independent reviewer has inspected material areas or reviewer unavailability is logged;
- no claim of qualified engineering/customer acceptance or production functionality without real evidence.

**No automatic implementation permission:** this handover authorizes a *handover/documentation change*, not code mutation, environment secrets access, external deployment, schema migration, production payments or actual project acceptance. Respect active owner and FMCIS collaborator boundaries, and prefer reviewable small patches.
